Making Kubernetes
fluent in AI apps

A Headlamp plugin that turns scattered Kubernetes resources into a single AI application view, with inference-engine metrics, GPU telemetry, and kernel-level diagnostics.

Date 2026-06-03 Stage v1.0 scoped, demo built Companion Topology demo (preceded this page)

The problem

Operators run AI workloads in the dark

An ML application on Kubernetes is never one resource — it’s a model, plus an app pod, plus a vector database, plus storage, plus secrets, plus routing. Today operators see those as scattered objects with no application identity. Headlamp shows pods and deployments; it doesn’t know which ones belong to a given AI application, or whether that application is healthy as a whole.

The diagnostics gap is worse. The metrics that matter for AI — time-to-first-token, KV-cache pressure, prefix-cache hit rate, GPU utilization, NCCL retransmits — live behind raw Prometheus endpoints, DCGM exporters, and eBPF tools. Each one is a separate surface with its own conventions, and none of them are joined up to the workload they describe.

The bet

Three concepts make Kubernetes AI-fluent

1. A Project is a real object. A small CRD groups every resource of one ML app. Ready/Degraded/Empty at a glance. Headlamp aggregates per-project throughput, latency, cost, sessions. The pile becomes a thing.

2. AI-shaped diagnostics, in one place. Per-model inference metrics from vLLM / Ray Serve / TEI. GPU telemetry from DCGM when present. Kernel-level diagnostics (DNS to HuggingFace, OOM kills, CUDA allocations, NCCL retransmits) via Inspektor Gadget. Nothing new for ops to install — the plugin uses what’s already standard.

3. AKS conveniences, layered on top. KAITO presets, Workload Identity wiring, ACR pull-secrets, Gateway API HTTPRoute, Azure OpenAI credential helper — the AKS-specific paper-cuts an operator hits when standing up an AI workload on Azure. These ship as a separate layer that loads only on AKS clusters, and they drive everything from Kubernetes labels and Azure Portal deep-links — no Azure Resource Manager SDK in the plugin. When the kaito-project organization is ready to ship this independently, the layering means it’s a config change, not a refactor.

Scope

What v1.0 ships — and what it deliberately doesn’t

v1.0 ships

  • Project CRD + controller; Projects list, Resources tab, create wizard
  • Observability tab: per-model TTFT / TPOT / throughput / KV-cache
  • GPU telemetry panel (DCGM via Prometheus, when both detected)
  • Inspektor Gadget integration for kernel-level diagnostics
  • AKS overlay: KAITO preset, Workload Identity, ACR, HTTPRoute, AOAI credentials
  • Engine adapters: vLLM, Ray Serve, HuggingFace TEI
  • Graceful fallback when any optional dep (Prom, DCGM, IG, KAITO) is absent
  • Stretch: Topology view (visual proof already built)

Out of scope (and that’s the point)

  • Replacing the AI Runway deploy wizard
  • Generic Inspektor Gadget browser
  • Alerting, on-call, or thresholds
  • GitOps integration
  • Cross-cluster Project views (v1.1+)
  • Any Azure ARM / AWS / GCP cloud SDK use, at any version
  • Long-term metric or gadget-result persistence
